# 自适应决策访谈

Keelson 的使用者不需要掌握软件架构术语。访谈是隐藏控制逻辑：只找出真正属于所有者的决定，让每个问题都容易回答，然后尽快回到实现。普通工作**不是**问卷；只有用户明确要求“深挖一下 / 压力测试这个方案”时，才深入走完同一棵决策树的重要分支。

## Question Protocol：每次打断都必须值得
<!-- keelson: id=interview.protocol | without: Agent 会问没必要的问题，把实现选型甩给用户，或者自己都说不清答案会改变什么 | sunset: never -->

提问前先在内部回答：

1. **后果** —— 这个答案会改变什么用户可见行为、验收边界、风险、成本、兼容承诺或长期决定？
2. **所有权** —— 答案属于仓库/现实、Agent 的工程判断，还是所有者的意图/风险偏好？
3. **可调查性** —— 代码、测试、文档、telemetry、官方文档或一个小实验能否回答？
4. **可逆性** —— 默认值猜错后，是局部低成本修正，还是昂贵/不可逆？
5. **信息价值** —— 它是不是最可能改变下一个安全切片的那个未决项？
6. **默认值** —— 如果用户说“你来决定”，你有依据的选择是什么？

如果说不清实质后果，或者答案根本不属于用户，就**不要问**。自行调查、采用可逆默认值，或留到后续切片。

## 第一个问题前先做盲点扫描
<!-- keelson: id=interview.blindspots | without: 访谈只能处理用户已经意识到的未知项，领域特有的失败模式仍会被漏掉 | sunset: never -->

开始访谈前做一次紧凑的风险触发扫描。只加载 `design-lenses.md` 中当前变更真正触发的行，先检查仓库和现有契约。重点寻找会改变设计的 unknown unknowns：破坏性数据语义、权限边界、外部兼容、重复/重试、迁移/回滚、故障恢复、可访问性、有测量依据的性能/成本，以及 AI 非确定性。

发现盲点**不等于**马上问用户。先路由成：已有保证、工程默认值、小实验、验收/证据场景，或者真正属于所有者的决定。只有最后一种才提问。

## 一次一个决定，优先“识别”而不是“回忆”
<!-- keelson: id=interview.one-at-a-time | without: 问题墙会压垮用户，而开放式技术术语会逼新人编造架构偏好 | sunset: never -->

提问前读取 `keelson ask list --json`，已确定的答案不得重复询问；新证据确实要求重开时使用 `ask reopen <id> --reason`。每轮至多提出三个独立、前提已满足的用户决定；依赖问题等待前提解决。用 `ask add`、`settle`、`assume`、`frontier` 保存归属、答案和依据，不可逆决定不能靠假设通过。优先用具体场景，并让用户“识别”而不是凭空“回忆”：

- 用用户自己的语言描述场景；
- 给 2–4 个**结果真正不同**的选项；有帮助时给每个选项附一条简短的 **工程影响**，不要让用户自己猜实现后果；
- 推荐一个默认值，并只说最重要的一条理由；
- 真有必要时只点出一个关键取舍；
- 合法时提供 **“不确定 / 采用你的推荐”**；
- 选项都不合适时允许自由回答。

差的问题：“Postgres 还是 MongoDB？”

更好的问题：“同一类记录是否允许不同用户自由增加不同字段，还是所有记录应遵循同一套字段结构？如果可变字段不是核心功能，我建议统一 schema，这样验证和迁移更简单。**工程影响：** 如果项目已经使用关系型数据库，直接沿用现有数据库建立固定字段表即可，不需要新增另一种数据库。”

不要要求用户记住前面几轮的上下文。问题里简短带上使它成立的事实或约束。

## 让问题一眼能看懂
<!-- keelson: id=interview.presentation | without: 正确的问题被埋在长段落里、推荐被误解成强制要求，或者用户无法快速看出各选项差别 | sunset: never -->

需要选项时，面向用户保持极简：

**需要决定：** <一个大白话问题>

- A. <可观察结果>  
  **工程影响：** <真正重要的数据模型 / 权限 / API / 运维后果>
- B. <可观察结果>  
  **工程影响：** <真正重要的实现后果>
- C. <只有真的不同才出现>  
  **工程影响：** <真正重要的实现后果>
- 不确定 —— 采用你的推荐

**推荐：** <选择>，因为 <一条决定性理由>。  
**建议实现：** <优先复用现有技术栈；只有仓库证据支持或各选项确实不同，才写具体组件>。

只有“为什么现在必须决定”不明显时，才额外加一句说明。不要向用户暴露内部 lens 清单、评分过程或推理链。如果用户先要求解释，先在正常聊天里解释，再决定是否需要重问。

## 说明足够的实现后果
<!-- keelson: id=interview.implementation | without: 用户理解了产品选择，却不知道它在真实系统里意味着什么，或者 Agent 只堆技术名词却没有架构上下文 | sunset: never -->

写技术栈之前先检查仓库真实使用的技术。问题卡要把工程后果说具体，但不能变成“技术选购”：

- 现有技术栈能实现时，直接说明在现有栈里会改什么：schema/table、权限模型、endpoint/contract、background job、cache、migration 或测试面。
- **不需要新增技术时明确说不需要。** 不要为了显得专业就随便加 Redis、Kafka、新数据库、新 service 或新 framework。
- 不同选项真的对应不同架构时，才点名可能使用的具体技术/类别以及原因，例如“现有 Postgres + ACL 表足够”与“这个规模的团队广播需要 queue”。
- 绿地项目没有既定栈时，用**建议方向**而不是假装确定：“关系型数据库，例如 Postgres”“对象存储”“只有异步 fan-out 需要时才引入 queue”。
- 优先解释用户真正能理解的工程后果：一致性、迁移难度、运维成本、故障方式、权限边界和未来可逆性。

技术只是产品后果明确后的解释上下文，不能代替真正需要用户决定的问题。

## 按依赖顺序决定，并主动控制范围
<!-- keelson: id=interview.order | without: 产品边界还没确定就开始选技术，或者访谈一路扩张成尚未需要的未来架构 | sunset: never -->

大致按依赖顺序解决：

**问题/角色 → 范围与非目标 → 可观察行为 → 数据/权限不变量 → 外部契约 → 故障语义 → 昂贵架构 → 实现细节**

只有上游答案会改变后续分支时才问。发现 grab-bag 或 rabbit hole 时，把独立领域拆开，先确认哪个领域能解锁下一个真正有用的切片，把纯未来需求停放起来，不为“以后也许需要”提前设计。

某个实现细节即使存在多个合理方案，只要可逆，就不因为“有选择”而升级成用户问题。

## 适配表达，不给用户画像分级
<!-- keelson: id=interview.adaptive | without: 新人被迫猜术语，熟练用户收到冗长教程，项目还会持久保存脆弱的初级/高级标签 | sunset: never -->

所有人默认都先用场景和大白话。行为理解以后，确实有帮助时再用一句话补工程术语。所有者已经准确使用术语时直接沿用，并缩短解释。

永远不要让用户自选 beginner/intermediate/expert，也不要持久化这种标签。只根据当前对话自适应。 `guide: true` 增加的是教学：为什么重要、这个概念叫什么、什么时候该重审；它不增加 gate，也不增加强制问题数量。

## “我不知道”是有效答案
<!-- keelson: id=interview.uncertain | without: 用户被迫编造技术偏好、同一个问题反复出现，或本可由默认值/原型解决的选择阻塞整个工作 | sunset: never -->

把不确定当作路由信息：

- **现实拥有答案** → 自己调查。
- **可逆工程选择** → 沿用项目先例或采用推荐默认值。
- **属于用户但难以想象** → 给最小示例、payload、草图、对比或一次性原型。
- **性能/成本未知** → 先测量，再决定是否增加机制。
- **高影响且仍未知** → 只阻塞真正依赖它的切片。
- **用户先要求解释而不是回答** → 先在正常聊天里解释，不要立刻弹回同一张问题卡。

不要把“我不知道该选什么技术”变成技术投票；把它翻译成真正会影响技术选择的产品属性或运行约束。

## 回读结果、写回真相、及时停止
<!-- keelson: id=interview.stop | without: 答案只留在聊天里、同一个决定被重复询问，或者普通开发变成没完没了的访谈 | sunset: never -->

得到答案后，用一句话确认 **决定 + 后果**，只把长期有效的结果写入其所属工件，然后重新计算 decision frontier。不要保存访谈流水账。

普通工作中，只要下一个纵向切片已经具备：
- 清楚的可观察结果；
- 必要的边界/非目标；
- 没有真正阻塞它的 owner-owned 未决项；
- 明确的 acceptance / evidence 路径；

就停止提问。后续切片的问题可以保持 open，但不阻塞当前工作。只有用户明确要求 深挖 / 压力测试时，才继续走完请求边界内的**重要**分支；仍然拒绝纯未来假设和低价值实现细节。
