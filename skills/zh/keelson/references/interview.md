# 自适应决策访谈

Keelson 的使用者只需用普通语言描述目标。Agent 根据未决选择及其后果自动决定探索深度；用户无需知道 Skill 名称、特殊提示词或访谈模式开关。先调查，再让属于用户的决定容易回答，然后回到用户请求的工作。

## 由工作本身触发需求探索
<!-- keelson: id=interview.activation | without: 用户必须知道要主动要求深度访谈，模糊目标和影响重大的假设因此未经检查就进入实现 | sunset: never -->

出现新目标、实质性补充，或足以改变已定前提的新证据时，先检查相关仓库事实和已有答案，再决定深度：

- **清楚且有边界：** 结果、验收与相关约束已经明确，直接推进；常规小修改或事实解释不需要访谈仪式。
- **一个关键缺口：** 询问当前已就绪、信息价值最高的用户决定，给出推荐和理由；得到答案后重新判断。
- **相互关联的不确定性：** 目标或成功标准不清、产品选择存在依赖、需求相互冲突，或尚未确定的权限/数据/兼容/迁移承诺会实质改变设计。自动沿相关决策分支深入，在确定依赖它们的设计前解决。只要这些选择未定，“加个团队共享功能”这样的普通请求就足够触发，不要询问是否启用深度访谈。

按缺失的决定与后果触发，不靠关键词或任务大小。高风险问题也可能已有契约可循。按 `design-lenses.md` 检查领域风险，自行调查事实，只问需要所有者判断的事。后续答案暴露新分支时使用同一规则；没有足以重开的新证据，就复用已定选择。

需求探索不会扩大授权：讨论方案仍然只读；已授权修改在相关决定解决后继续实现。用户明确要求扩大评审范围时可以扩大范围，但自动探索不以此为前提。

## 先发现目的，再选择实现手段
<!-- keelson: id=interview.purpose | without: 访谈只优化用户提出的功能，背后的真实问题与成功标准却未经确认 | sunset: never -->

从证据出发：谁在什么情境下想完成什么，现在被什么阻碍，出现什么可观察改善才算成功，哪些约束已经确定？请求和仓库已说明的部分自行填入。这些是内部判断线索，不是必须问完的五道题。

区分明确要求与建议手段。“加一个仪表盘”可能是为了更快决策、发现异常或提交报表，对应不同产品。目的不明时，询问一个近期具体情境，或能区分这些结果的对比。检查因果假设：现有流程的更简单调整能否达到同样结果，去掉建议机制还缺什么？把自己的理解当作有来源的假设，不替用户宣称隐藏意图。用户明确指定的手段应尊重；确有冲突时先说明，再建议调整。

只在会改变决定时使用工程原理：成功标准用可观察验收场景，边界用领域术语和不变量，性能主张先测量，长期承诺考虑可逆性，用最小端到端切片检验方向。不要变成理论教学、技术选型问卷或无止境地追问“为什么”。下一项设计选择和验证路径已经明确，就停止追究原因。

小请求也要检查结果：重放拟议的使用过程，原始困扰是否仍然存在？保留数据不等于必须保留原来的展示方式。如果两种合理体验会影响问题是否被解决，而负责人尚未选择，就在编码前用一个具体对比、推荐和理由确认。若请求已经确定体验，写出可观察验收后直接推进。范围小并不能证明目的已明确。

## Question Protocol：每次打断都必须值得
<!-- keelson: id=interview.protocol | without: Agent 会问没必要的问题，把实现选型甩给用户，或者自己都说不清答案会改变什么 | sunset: never -->

提问前先在内部回答：

1. **后果** —— 这个答案会改变什么用户可见行为、验收边界、风险、成本、兼容承诺或长期决定？
2. **所有权** —— 答案属于仓库/现实、Agent 的工程判断，还是所有者的意图/风险偏好？
3. **可调查性** —— 代码、测试、文档、telemetry、官方文档或一个小实验能否回答？
4. **可逆性** —— 默认值猜错后，是局部低成本修正，还是昂贵/不可逆？
5. **信息价值** —— 它是不是最可能改变下一个安全切片的那个未决项？
6. **默认值** —— 如果用户说“你来决定”，你有依据的选择是什么？

如果说不清实质后果，或者答案根本不属于用户，就**不要问**。自行调查、采用可逆默认值，或留到后续切片。

## 第一个问题前先做盲点扫描
<!-- keelson: id=interview.blindspots | without: 访谈只能处理用户已经意识到的未知项，领域特有的失败模式仍会被漏掉 | sunset: never -->

开始访谈前做一次紧凑的风险触发扫描。只加载 `design-lenses.md` 中当前变更真正触发的行，先检查仓库和现有契约。重点寻找会改变设计的 unknown unknowns：破坏性数据语义、权限边界、外部兼容、重复/重试、迁移/回滚、故障恢复、可访问性、有测量依据的性能/成本，以及 AI 非确定性。

发现盲点**不等于**马上问用户。先路由成：已有保证、工程默认值、小实验、验收/证据场景，或者真正属于所有者的决定。只有最后一种才提问。

## 按复杂度组织问题，优先“识别”而不是“回忆”
<!-- keelson: id=interview.one-at-a-time | without: 问题墙会压垮用户，而开放式技术术语会逼新人编造架构偏好 | sunset: never -->

提问前先读取已有决定。当前请求授权修改项目时，在其活动变更上用 `ask add`、`settle`、`assume`、`frontier` 保存归属、依赖、答案和依据。已确定的答案不得重复询问；新证据确实要求重开时使用 `ask reopen <id> --reason`。只读探索即使已有活动变更，新答案也只留在对话中；获得实施或持久化授权后才写入。

就绪 frontier 只包含有实质后果的未决选择，不收集所有可能问题。合并同一决定的重复问法，先调查事实，把真正独立的未来工作保留未决状态后延期。某轮问题过多时，检查是否尚有一个上游目的未定，导致多个下游问题其实还不能问；不同的重要决定仍分别保留。访谈没有最低题数或固定上限：已经清楚就零提问，一个缺口问一题，选择相互关联时问当前就绪层。不能为了简短跳过未决权限、验收或长期承诺。

简单缺口每轮问一个最有价值的就绪用户决定（`ask frontier --limit 1`）。存在相互依赖的不确定性时，**一轮问完当前所有前提已确定的用户问题**（`ask frontier --all`），按主题分组，每题给推荐和理由。宿主限制题数时，用一个受支持的文本问题打包，或分批呈现同一轮；本轮前提未确定前不进入依赖问题。推荐不等于答案：除非已有授权明确委托该选择，否则等待用户回答。仓库和现实事实由 Agent 调查，不交给用户猜。不可逆决定必须明确确定，不能靠假设通过。优先用具体场景，并让用户“识别”而不是凭空“回忆”：

- 用用户自己的语言描述场景；
- 给 2–4 个**结果真正不同**的选项；有帮助时给每个选项附一条简短的 **工程影响**，不要让用户自己猜实现后果；
- 推荐一个默认值，并只说最重要的一条理由；
- 真有必要时只点出一个关键取舍；
- 合法时提供 **“不确定 / 采用你的推荐”**；
- 选项都不合适时允许自由回答。

差的问题：“Postgres 还是 MongoDB？”

更好的问题：“同一类记录是否允许不同用户自由增加不同字段，还是所有记录应遵循同一套字段结构？如果可变字段不是核心功能，我建议统一 schema，这样验证和迁移更简单。**工程影响：** 如果项目已经使用关系型数据库，直接沿用现有数据库建立固定字段表即可，不需要新增另一种数据库。”

不要要求用户记住前面几轮的上下文。问题里简短带上使它成立的事实或约束。

## 让问题一眼能看懂
<!-- keelson: id=interview.presentation | without: 正确的问题被埋在长段落里、推荐被误解成强制要求，或者用户无法快速看出各选项差别 | sunset: never -->

面向用户保持紧凑。每轮先用一句话说明当前理解和答案会解锁什么。多题编号，便于简短回复；只有一题时可省略编号。

**需要决定：** <与当前场景相关的一个大白话问题>
- A. <可观察结果>；B. <真正不同的结果>。
- **推荐：** A，因为 <决定性理由>；<确有必要时说明主要代价>。

确实改变结果时才增加选项；允许自由回答，合法时可明确选择“采用你的推荐”。没有推荐依据时，用中立示例或简短开放题，不强造答案。“我不知道”本身不等于委托决定。**建议实现：** 只有具体工程后果能帮助选择时才补一句，不在每个选项下重复相同解释。

用户可以回答“同意推荐，除了第 2 项……”。仅对已明确展示的选择应用这个回答，漏答的项继续保持未决。不要暴露内部镜头清单或推理过程；用户要求解释时先解释。长期结果按 `writing.md` 保存，但不把五项分组建议当成 frontier 的题数上限。

## 说明足够的实现后果
<!-- keelson: id=interview.implementation | without: 用户理解了产品选择，却不知道它在真实系统里意味着什么，或者 Agent 只堆技术名词却没有架构上下文 | sunset: never -->

写技术栈之前先检查仓库真实使用的技术。问题卡要把工程后果说具体，但不能变成“技术选购”：

- 现有技术栈能实现时，直接说明在现有栈里会改什么：schema/table、权限模型、endpoint/contract、background job、cache、migration 或测试面。
- **不需要新增技术时明确说不需要。** 不要为了显得专业就随便加 Redis、Kafka、新数据库、新 service 或新 framework。
- 不同选项真的对应不同架构时，才点名可能使用的具体技术/类别以及原因，例如“现有 Postgres + ACL 表足够”与“这个规模的团队广播需要 queue”。
- 绿地项目没有既定栈时，用**建议方向**而不是假装确定：“关系型数据库，例如 Postgres”“对象存储”“只有异步 fan-out 需要时才引入 queue”。
- 优先解释用户真正能理解的工程后果：一致性、迁移难度、运维成本、故障方式、权限边界和未来可逆性。

技术只是产品后果明确后的解释上下文，不能代替真正需要用户决定的问题。

## 按依赖顺序决定，并主动控制范围
<!-- keelson: id=interview.order | without: 产品边界还没确定就开始选技术，或者访谈一路扩张成尚未需要的未来架构 | sunset: never -->

大致按依赖顺序解决：

维护紧凑的决策树：每个未决选择标明前提，以及它会改变的结果。每个答案解决一个分支，也可能暴露新分支。每轮后重新计算已就绪的问题；复杂轮次问完整的就绪用户问题集合，每题给推荐和理由；等待这些答案后，再沿新解锁的分支继续。调查仍在进行意味着前提未定，不代表可以猜测。完整决策树留在内部，只展示当前问题和简短结果。

**问题/角色 → 范围与非目标 → 可观察行为 → 数据/权限不变量 → 外部契约 → 故障语义 → 昂贵架构 → 实现细节**

只有上游答案会改变后续分支时才问。发现 grab-bag 或 rabbit hole 时，把独立领域拆开，先确认哪个领域能解锁下一个真正有用的切片，把纯未来需求停放起来，不为“以后也许需要”提前设计。

某个实现细节即使存在多个合理方案，只要可逆，就不因为“有选择”而升级成用户问题。

## 适配表达，不给用户画像分级
<!-- keelson: id=interview.adaptive | without: 新人被迫猜术语，熟练用户收到冗长教程，项目还会持久保存脆弱的初级/高级标签 | sunset: never -->

所有人默认都先用场景和大白话。行为理解以后，确实有帮助时再用一句话补工程术语。所有者已经准确使用术语时直接沿用，并缩短解释。

永远不要让用户自选 beginner/intermediate/expert，也不要持久化这种标签。只根据当前对话自适应。 `guide: true` 增加的是教学：为什么重要、这个概念叫什么、什么时候该重审；它不增加 gate，也不增加强制问题数量。

## “我不知道”是有效答案
<!-- keelson: id=interview.uncertain | without: 用户被迫编造技术偏好、同一个问题反复出现，或本可由默认值/原型解决的选择阻塞整个工作 | sunset: never -->

把不确定当作路由信息：

- **现实拥有答案** → 自己调查。
- **可逆工程选择** → 沿用项目先例或采用推荐默认值。
- **属于用户但难以想象** → 给最小示例、payload、草图、对比或一次性原型。
- **性能/成本未知** → 先测量，再决定是否增加机制。
- **高影响且仍未知** → 只阻塞真正依赖它的切片。
- **用户先要求解释而不是回答** → 先在正常聊天里解释，不要立刻弹回同一张问题卡。

不要把“我不知道该选什么技术”变成技术投票；把它翻译成真正会影响技术选择的产品属性或运行约束。

## 把答案接入同一条交付流程
<!-- keelson: id=interview.continuity | without: 需求探索止于聊天摘要，实现和审查却围绕另一目标或丢失用户决定 | sunset: never -->

在写入授权内，同一目标的补充继续使用同一个 change。`request.md` 保留原始需求与重要补充；`decisions.json` 用稳定 ID 保存结构化选择、依赖、答案和依据。无需独立访谈报告，也不要求用户手动交接。明确的小修改使用既有 What/Acceptance/Decisions 即可，不为填满决策树而制造问题。

每个重要答案写入它影响的工件：

| 答案明确了 | 写入或更新 |
|---|---|
| 真实问题、角色、期望改善 | `change.md → Why` 与 `What`；只有改变项目级事实时才调整 `INTENT.md` |
| 范围、非目标、被否方案 | `What`、`Decisions`；明确延期的工作放入任务系统或路线图 |
| 可观察行为或不变量 | `Acceptance` 及相关 delta 场景；有帮助时引用决定 ID |
| 工程后果 | `How`、受影响任务或切片，以及验证路径 |
| 未决前提或答案变化 | 原决定及受影响的依赖决定、待决问题和验收；每次重开说明原因 |

用短引用串起关系，例如“D-visibility → 仅本人可访问场景 → 创建/列表切片 → 访问检查”，不要重复建一份追踪文档。较长的支撑材料只存一处，需要时在 `context.json` 为 implement/check 声明路径。启动前核对记录的结果与原始需求、重要分支和完整已登记 frontier，然后自动运行 `start`、加载 `context --phase implement`。计划变化使旧启动记录失效。

上游答案改变时，检查所有依赖它的已定选择；有影响的带原因重开，并在继续依赖实现前更新验收、delta 和任务。CLI 不会自动重开子孙决定或改写文档；Agent 负责这一判断。保留无关的既定答案。独立审查加载 `context --phase check`，沿“目的 → 决定 → 行为 → 证据”复核，也检查非目标。落地后按 `reconcile.md` 回写稳定行为和理由，后续对话复用。

## 回读结果、写回真相、及时停止
<!-- keelson: id=interview.stop | without: 答案只留在聊天里、同一个决定被重复询问，或者普通开发变成没完没了的访谈 | sunset: never -->

得到答案后，用一句话确认 **决定 + 后果**，仅在当前请求授权写入时，把长期有效的结果写入其所属工件，然后重新计算 decision frontier。不要保存访谈流水账。

当前评审范围或下一个实现切片具备以下条件时停止提问：
- 清楚的可观察结果；
- 必要的边界/非目标；
- 没有会改变其结果或设计承诺的用户未决项或隐含假设；
- 明确的 acceptance / evidence 路径；

深入探索时，解决所有会改变当前结果或设计承诺的重要分支，包括前面答案新暴露的下游选择。共享架构仍依赖高影响未决项时，不得把切片当成已经安全。独立工作可以继续：把真正属于后续的未决问题移到 ROADMAP 或单独的 change，保留其依赖和未决状态。`start` 检查整个当前 change，不允许把阻塞项留在当前变更中却宣称该变更已就绪。拒绝纯未来假设和低价值实现细节。回到用户请求的工作，无需“结束访谈”口令，也不重复索取已有授权。

对于已落盘的访谈，只有 `keelson ask frontier --all --json` 返回 `complete: true`，才能说已登记的树全部确定。问题列表为空也可能是调查未完、依赖阻塞或假设未确认。同时检查当前目标、边界和领域风险是否还有未登记的重要分支：图已完成不能证明发现已穷尽。只读请求的新发现仍保留在对话中。
