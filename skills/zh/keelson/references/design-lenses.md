# 风险触发式设计镜头

这些是 **Agent 内部镜头，不是问卷**。只启用当前变更真正触发的镜头。先读仓库；只有剩下的不确定性属于用户、而且会影响结果时才提问。

## 触发镜头，不走全量问卷
<!-- keelson: id=lenses.triggered | without: 每个功能都被迫走巨型架构清单，或者真正重要的跨领域风险被漏掉 | sunset: never -->

| 镜头 | 常见触发 | 提问前先检查 | 典型结果 |
|---|---|---|---|
| 用户 + 领域 | 新流程、含糊名词、多角色 | 谁在做什么、现有行为、共享语言、bounded context | 场景/非目标；术语真重要时才进 glossary |
| 数据 + 完整性 | 持久化、schema、导入导出、删除、金额 | 所有权、不变量、生命周期、保留、迁移、审计/对账 | requirement + 迁移/回滚检查 |
| 安全 + 隐私 | 登录、权限、secret、PII、上传、不可信输入、工具 | 资产/数据流、最小权限、信任边界、滥用、验证 | 负向 acceptance + 安全检查 |
| 并发 + 异步 | queue、webhook、worker、实时、多写者 | 重复、顺序、幂等、重试、超时、取消、部分失败 | 重复/乱序/故障测试 |
| 兼容性 + 迁移 | 公共 API、event/schema/config/存储格式 | 现有消费者、breaking 定义、弃用、rollout、rollback | 兼容契约 + rollout |
| 可靠性 + 运维 | 关键路径、后台任务、外部依赖 | 失败表现、恢复、可观测性、安全降级 | 恢复测试 + metric/log/runbook 指针 |
| 性能 + 成本 | 明确延迟/吞吐/数据量/成本目标、测出的热点 | workload、目标/SLO、基线、资源上限 | benchmark/load check；不凭想象加缓存 |
| 界面 + 可访问性 | UI、表单、交互流程 | 主任务、错误/恢复、键盘/focus、可理解语言 | UI/accessibility acceptance |
| AI + 非确定性 | LLM、Agent、RAG、模型/工具调用 | eval case、fallback、数据边界、injection、工具授权、可复现性 | eval 集 + 安全/fallback acceptance |

触发某个镜头只意味着检查这个维度，绝不意味着把这一行所有问题问给用户。

## 把风险变成证据
<!-- keelson: id=lenses.evidence | without: 设计评审留下很多散文，但重要性质没有在后续变化中得到保护 | sunset: never -->

每个触发镜头最终只落成一种或几种结果：
- 已有 spec/rule/test 已保证 → 直接复用；
- 属于所有者的决定 → 在 decision frontier 只问那个问题；
- 工程不变量 → 窄作用域 rule，能自动化时优先 fitness/check；
- 验收/证据义务 → 加入对应的故障/兼容/安全/性能/迁移/可访问性场景；
- 明确不在范围内 → 如果不说明会像遗漏，就点名一次。

不要因此创建一份通用“非功能需求大全”。

## 优先不可逆风险
<!-- keelson: id=lenses.priority | without: Agent 忙着优化可逆细节，却对数据损失、权限、兼容性或迁移默默猜测 | sunset: never -->

大致按这个顺序解决：不可逆数据/安全/生产副作用 → 对外兼容/迁移/昂贵架构 → 故障/并发下的正确性 → 用户可见行为/可访问性 → 有测量依据的可靠性/性能/成本 → 可逆实现偏好。

性能机制先测量再添加。安全镜头内部使用紧凑循环：**我们在做什么 → 什么可能出错 → 怎么处理 → 证据能否证明做得够好**。优先把重要性质做成可执行 fitness check，而不是依赖评审时有人记得提醒。
