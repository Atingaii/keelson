# 发现真正想要的是什么

用户往往没法在第一句话里把完整需求说清楚，经验较少的开发者也未必知道哪些选择是该由自己做的。发现阶段要在任何人挑数据库之前，先找到请求背后的问题。

## 先谈场景，再谈技术
<!-- keelson: id=discover.scenario-first | without: 第一个问题就是负责人答不上来的技术选型，产品被他们的猜测塑形 | sunset: never -->

当请求是一个产品想法（"做一个团队知识库"、"加上协作"）时，不要问存储、框架或表结构。先问哪种用法处在中心，给出的备选要在"用户会做什么"上真正不同：

> 下面哪一种最接近大家用它做的第一件事？
> A. 几个人编辑同一批文档。
> B. 把公司资料收集起来，用来搜索。
> C. 把资料交给一个助手，由它回答问题。
> D. 最终都要；第一版应该先选一个。
> 第一版我建议只选一个：权限、搜索、助手、共同编辑各自都带来复杂度，叠在一起会把项目拖停。

每个发现类问题都由同样六部分组成：问题、一个具体场景、推荐、理由、备选、取舍。负责人说"不知道"时，用一个情境替代术语（"想象两个人同时打开同一页。两个人都应该能打字吗？"）、一张小草图，或一个用完即弃的实验。绝不把术语再重复一遍、说得更响。

## 哪些未知该提出来
<!-- keelson: id=discover.frontier | without: 要么每个未知都变成问题、什么都开不了工，要么代理自己拍板了产品问题 | sunset: never -->

提问之前先把每个未知归类：

| 未知 | 处理 |
|---|---|
| 能从代码、测试或文档里查到 | 自己读；绝不问 |
| 项目已有惯例 | 跟随惯例；在写回里提一句 |
| 低风险、容易撤销 | 自行决定，在你的授权范围内记为已确认 |
| 纯技术、负责人没有理由关心 | 选一个合理默认；用一行说明 |
| 改变产品对用户的行为 | 问，并附推荐 |
| 改变长期架构、成本或对外承诺 | 先解释，再确认 |
| 破坏数据、扩大权限、触及生产 | 永远明确确认 |

只有答案会改变结果的问题才交给负责人。其余都是默认值，或是落地前会浮现出来的 `(assumed)` 决策。

## 只在决策前沿提问
<!-- keelson: id=discover.decision-frontier | without: the agent either interrupts for facts it could investigate, invents user-owned intent, or asks low-value questions whose answers do not change the work | sunset: never -->

提问前，先按“谁有能力解决这个缺口”来分类：

| 缺口 | 处理 |
|---|---|
| 仓库或上下文已经确定 | 直接使用，并在写回中指出依据 |
| 属于现实世界（代码行为、API 契约、benchmark、依赖能力） | 自己调查，或做一个小实验 |
| 属于用户且会阻塞结果（目标、范围、验收、风险容忍度、公开承诺） | 只问一个问题 |
| 不阻塞，或很容易撤销 | 按授权决定，或留给后续切片 |
| 证据已经耗尽 | 标为 UNKNOWN；不要把不确定性改写成用户的观点 |

选择“实际信息价值”最高的问题：哪个答案最可能改变下一个切片，再乘上猜错它的代价。不需要真的算分。问题保持中性；有帮助时给出具体选项和你的推荐。得到答案后更新写回，再重新判断决策前沿。“只问一个问题”只用于**真正阻塞工作的不确定性**，不是仪式：没有由用户掌握的关键缺口时，一个问题都不要问，直接推进。

## 范围守卫
<!-- keelson: id=discover.scope-guard | without: 第一个请求就同时要五个独立领域，集成风险、调试成本和需求变动叠加放大 | sunset: never -->

当一个请求捆着好几个领域（身份、支付、实时协作、助手、插件、移动端），把它们点名为独立领域并提出顺序：其他领域都依赖的那个先做，其余作为后续里程碑写进 `ROADMAP.md → Next`。理由不是代码写不出来，而是每多一个领域，前面那些出错的方式就成倍增加，而此时还什么都没验证过。用大白话把这一点说出来。

## 先探索，再承诺
<!-- keelson: id=discover.explore | without: 一个便宜的实验就能用证据解决的问题，却被逼成了抽象决策 | sunset: never -->

当选择可逆而负责人拿不准时，不要催着做决定。提供一个 spike、原型、mock 或 benchmark，规模刚好回答一个问题：两个小 UI 变体供挑选；加缓存之前先 benchmark；采用某个库之前先 spike。把结果作为证据记进 ledger（`### Note:`），把它产生的决策记到 `## Decisions` 下。

## 引导模式
<!-- keelson: id=discover.guided | without: 正在学习的负责人拿到一堆选择却没有做选择所需的背景，从自己做出的选择里也学不到东西 | sunset: never -->

当 `config.yaml → guide` 为 true（或常驻块说明引导模式已开启）时，负责人正在通过构建来学习工程。工件不变，对话方式变：

- 把选择呈现为场景，附上推荐、理由、备选和取舍，用负责人自己的话说。工程术语放在解释之后、括号里，作为刚刚做出的决定的名字。
- 应用某条规则或约束时，用一句话解释它为什么存在。
- spec 变更落地后，用一段简短的教学说明收尾：关键决策、为什么这样做、它是哪种工程思想的实例、什么情况下该重新考虑。写在对话里，不写进项目文件。

引导模式从不改变记录什么、也不改变适用哪些门禁；它改变的是对话读起来的样子。
