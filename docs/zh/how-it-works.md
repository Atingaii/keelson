# 工作原理

创建或更新项目文档时，Agent 自动读取 `keelson guide writing`。工作与接续文档靠前呈现状态和可执行的下一步，契约先说明用途及行为；任务按有界动作编号、按结果分组，细节链接到所属文件。精简阅读面同时保留完整验收、整组就绪决策和原始签名证据。中英文模板保留相同的解析标题。这是 Agent 写作指导；`update` 刷新指导与目录导航，保留已有项目事实，后续由 Agent 在实际维护时应用。

项目事实和变更保存在 `.keelson/`，本机密钥、信任与会话保存在 Git 私有目录。默认初始化仅创建精简资料和宿主入口；`keelson guide` 从安装包读取指导，显式 `--vendor` 才复制指导。Hook 调用已安装的 `keelson hook`，不执行仓库内复制的 hook 脚本。

`start` 检查当前计划后进入实施；阶段上下文声明可版本化依赖，Claude Code、Codex 和 CodeBuddy hooks 对受支持的文件工具执行门禁并注入规范。manifest 记录生成文件摘要，以识别可安全更新的内容；旧版本通过已发布输出摘要迁移。详见[自动化机制与边界](automation.md)。

需求发现先区分真正目的与提出的实现手段，只追问有后果的用户决定；清晰任务无需问答。稳定的决定 ID 将答案连接到同一 change 的验收、delta 场景与实施切片；implement/check 上下文保留原始请求和决定。上游前提变化时，Agent 检查并重开受影响的后续决定，同步这些工件，再取得新的 start 凭据；CLI 不会自动理解并级联改写语义。独立审查检查证据是否证明用户目的已经达到。

`ask` 管理带归属、依赖、状态和依据的决策。`check` 记录真实执行结果及代码、契约摘要。`land` 检查验收和证据门槛，折叠规格并归档签名记录，写入中断可以恢复。

规格支持旧 h2 需求和 嵌套的 Requirements/h3 形式，围栏中的标题不算结构；合并需要保留未知章节。CLI 的测试证明结构和机制，不能证明所有真实宿主的行为相同。
